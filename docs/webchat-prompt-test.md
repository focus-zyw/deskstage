# 网页版模型手动验证测试包

目的:在写任何"隐藏浏览器驱动网页版模型"的代码之前,先手动验证网页模型
(DeepSeek 网页版 / 智谱清言)能否稳定产出**应用能直接吃**的输出。

下面的提示词与 `llmClient.ts + promptBuilder.ts` 实际发送的内容**逐字一致**,
只做了两处适配:

- 网页聊天没有 system role → 把 system 和 user 合并成一条粘贴(将来 webchat
  驱动的注入方式也是这么合并,测的就是真实场景)
- 空状态假设:没有观众画像/记忆事实/角色世界/上一段结尾/观众捣乱 recap
  (应用里会额外注入这些块,但它们不是格式风险的主要来源)

应用真实请求还带 `temperature: 1.1`、`response_format: json_object`、
`max_tokens: 4000`——网页版统统没有。所以本测试测的是网页模型**裸奔状态下**
的格式服从度,这是比"内容好不好笑"更关键的接入指标。

## 测试方法

1. **开全新会话**(不要在带历史的对话里测,避免上下文污染)
2. DeepSeek 网页版:**默认模式即可,不要开"深度思考(R1)"**——应用里用的是
   快速非思考模型,思考模式延迟差一个量级,没有参考价值。智谱清言同理
3. 整段复制提示词(从"你是一位"到最后一个字),一次粘贴发送
4. **等输出完全停止**再复制。如果中途断了,点"继续"让它输出完,或记下截断位置
5. 测试量:
   - 提示词 A(相声 JSON):**每家测 3 次**——格式稳定性是本测试的核心产出
   - 提示词 B(日常 JSON):每家 1 次
   - 提示词 C(单句回复):每家 1 次
6. 把模型的**原始输出原样**复制回来(带围栏、带"好的,以下是"之类多余文字也
   原样保留——解析器要 tolerate 的就是这些),贴回 ZCode 会话

## 提示词 A:相声模式主生成(格式压力最大)

话题取自真实话题池,关系卡取"子母哏"(权重最高、最常用),时间槽为深夜。

```text
你是一位擅长传统相声和网络脱口秀的资深喜剧编剧,给桌面双人情景剧写段子。角色设定：
- 甲（speaker 用 "A"）：精力充沛、爱吹牛、脑洞大、说话夸张，满嘴跑火车还特别得意，常用"我跟你说""好家伙"当口头禅
- 乙（speaker 用 "B"）：冷静毒舌、专拆台、话少但一针见血，惯用反问和吐槽拆穿甲的牛皮，偶尔冷幽默
- 两人是老搭档，互怼但有默契，节奏像传统相声里的逗哏和捧哏

本集关系状态（必须遵守,写进场景卡的 relationship 字段）：子母哏——逗捧轮流换手:前半段甲吹乙拆,后半段乙吹甲拆,换手要接得严丝合缝。关系只改变本集攻守,甲乙的基础性格与说话风格不变。

现实时间：现在是深夜，深夜还没睡、四周都很安静的氛围。段子的场景和情绪可以贴合这个时间段。

创作要求（这是喜剧，好笑比什么都重要）：
- 场景卡的 escalation 就是包袱节拍：前一拍铺垫、后一拍意外反转，最后一句必须是响底的包袱收束
- secret 是反转的底气：揭晓时要"出人意料但回头看合理"
- callback 是本集自己的梗：结尾回收前面埋的线，形成"老观众才懂"的呼应
- 台词全部口语化，像真说话，不要书面语；允许"哎""嚯""好家伙""就这？"这类语气词
- 关系决定说法：按本集关系状态写出"想说不敢说/嘴硬/试探/讨好"这些姿态差异，不要俩人从头吵到尾
- 话题活化：话题只是种子，把它翻译成当下年轻人真实的生活场景——具体的 app 名、场景、行为习惯、当代情绪，不要干巴巴围绕话题词打转

输出协议（严格遵守）：
- 只输出一个 JSON 对象，不要输出任何其他文字
- 先写场景卡再写台词，格式：{"card":{"relationship":"关系标签","scene":"具体场景一句话","goalA":"甲想要什么","goalB":"乙想要什么","secret":"被隐瞒的关键信息(一方或双方知道)","escalation":["节拍1","节拍2","节拍3"],"callback":"结尾回收的本集铺垫"},"dialog":[{"speaker":"A","text":"台词","action":"动作"},...]}
- dialog 必须逐拍实现 card.escalation；secret 在结尾反转揭晓；callback 必须回收本集前面埋的线
- speaker 只能是 "A" 或 "B"
- action 只能是这些词之一（禁止用 card 的字段名或其他词）：idle, talk, happy, laugh, shy, sleepy, wave, thinking, angry, sad, surprise, shake, jump
- 一段共 14~22 句，两人交替说话
- 每句口语化，不超过 25 个字
- 台词可在 text/action 外带可选演出字段(用在该用的地方,没有就省略,别每句都加)：
  "listenerAction":听者此刻的反应动作(词表同 action)、"delivery":"deadpan|excited|slow"(面瘫/兴奋/慢条斯理)、"pauseBefore":毫秒(包袱前 300~600 蓄势)、"pauseAfter":毫秒(只给响底的最后一句,900~1500 留白)

当前是【相声】模式：甲是逗哏（负责铺陈和抖包袱），乙是捧哏（用"哦？""好家伙""嗐！"这类短句接话、拆台）。结构：开头垫话 1~2 句，中间正活层层展开，最后 1 句必须是收底的包袱。

本段话题：深夜网购的冲动与后悔
请先定场景卡,再输出这一段完整对话的 JSON。
```

## 提示词 C:观众聊天回复(单句,非 JSON)

`generateUserChatReply("A", userText)` 的真实提示词,`userText` 用例:"今天上班被老板骂了,心情好差"。应用里还会注入观众画像/记忆 bits,此处为空状态。

```text
桌面双人情景剧互动。你是甲:精力充沛、爱吹牛、脑洞大、说话夸张,口头禅"我跟你说""好家伙"。观众朋友直接对你说了一句话,用你的口吻回一句。要求:15~25 字,口语化,像真说话;不要引号,不要 JSON。
今天上班被老板骂了,心情好差
```

## 评估核对清单(贴回后我会用 node 跑真解析器逐项核对)

**格式(接入的硬门槛)**

- [ ] 输出能被 `parseGeneratedDialog` 解析:容忍 ```json 围栏和前后杂文字
      (正则提取第一个 `{...}`),但 JSON 本身不能残缺/截断
- [ ] `dialog` 有效台词 ≥ 4 句(少于即整个生成失败),目标 14~22 句
- [ ] speaker 只有 "A"/"B" 且基本交替(非法行会被整行丢弃,丢多了就 fail)
- [ ] action 全部落在 13 词动作表内(非法会被归一为 talk,不算致命但扣分)
- [ ] 每句 ≤ 25 字左右、口语化
- [ ] 可选演出字段(listenerAction/delivery/pauseBefore/pauseAfter)格式合法
      (非法会被钳位或丢弃)

**内容(质量分)**

- [ ] 场景卡字段齐全,secret 在结尾"出人意料但回头看合理"
- [ ] callback 确实回收了本集前面埋的线(不是嘴上说说)
- [ ] 话题被活化成具体场景(app 名/行为/当代情绪),不是干巴巴绕话题词打转
- [ ] 关系姿态成立:子母哏有换手;甲有求于乙有"心虚+讨好"
- [ ] 甲乙声音可区分:甲吹、乙拆,没有从头吵到尾

**稳定性(决定能不能上)**

- [ ] 提示词 A 同一站点 3 次全部可解析 → 格式成功率 100%
- [ ] 3 次里 ≥1 次不可解析 → 需要在驱动层加自动重试/格式修复,成本 +1
- [ ] 输出是否被网页版截断(网页端 max output 限制,长 JSON 是重灾区)

**判定标准(建议)**

- A 三连全过、质量在线 → 值得投入阶段 2(隐藏 WebView2 驱动)
- 格式偶发失败但质量好 → 可做,驱动层加"解析失败自动追问一次"的补救
- 格式大面积跑飞 / 每次都截断 → 放弃该站点,换下一个靶子

## 结果记录(第 1 轮,2026-09-09 深夜)

| DeepSeek·C 单句 | ✅ | 30 字(≤40 内) | — |

**第 1 轮结论**:裸奔状态(无 json_mode、无 temperature)下,两家网页模型 **6/6 样本**
全部可被 `parseGeneratedDialog` 直接解析,零坏行、零非法 action、零截断、零未交替,
pauseBefore/pauseAfter 位置都放对了(响底前 300~600、响底后 1000~1200)。

待补:A 每家 ×3 的稳定性样本;延迟数据(手动测不了,阶段 2 spike 验)。
