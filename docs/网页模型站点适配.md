# 网页模型站点适配

网页版生成通道用系统 Edge 的独立 profile 打开站点标签页,经 CDP 注入脚本发送 prompt、
抓取回复。**站点知识的唯一事实源是 `src-tauri/src/webchat/sites.rs`**——调度器
(`webchat.rs`)只认 adapter 字段与方法,不出现 `if site` 分支;站点改版只改这一个文件。

## 当前站点

| id | 显示名 | 入口页 | 输入框 | 这条站点独有的坑 |
|---|---|---|---|---|
| `deepseek` | DeepSeek 网页版 | `chat.deepseek.com` | textarea / contenteditable | 圆形发送键启用晚于插入,填好后要补点一次 |
| `doubao` | 豆包网页版 | `www.doubao.com/chat/` | textarea / lexical contenteditable | 回复根节点是 `v_list_row`,与别的站点完全不同 |
| `qianwen` | 千问(通义)网页版 | `www.qianwen.com` | React 受控 contenteditable | 发送键只在**真实提交**后才启用,`insertText` 不触发提交 |
| `chatgpt` | ChatGPT 网页版 | `chatgpt.com` | Lexical contenteditable(`#prompt-textarea`) | 上千字的 `insertText` 会逐字建节点并冻死标签页,长 prompt 必须走粘贴 |
| `gemini` | Gemini 网页版 | `gemini.google.com/app` | Quill(`.ql-editor`) | 靠 `ql-blank` 类名认定"没编辑过",不摘掉就不启用发送键 |

`chatgpt` / `gemini` / `qianwen` 的选择器与交互策略移植自 `D:/web-tool` 的
`extension/content/{chatgpt,gemini,qianwen}.js` 以及它们的共享骨架 `runtime.js`
(`pasteReplace` / `fillContentEditable` / `settlePaste`)。

> **选择器是时点快照。** 三站移植后**尚未在真机上跑过**——本仓库只做了单元测试
> (脚本装配、占位符替换、站点 DOM 互不串味)与类型/构建校验。首次使用前请按设置页
> 「打开窗口 → 登录 → 查状态」走一遍;`查状态` 报"输入框未出现"就是该更新本表选择器了。

## adapter 字段

| 字段 | 作用 |
|---|---|
| `url` / `host` | 入口页;标签页归属判定(页面 URL **包含** `host` 即视为本站) |
| `composer_sels` | 输入框(顺序即优先级,取第一个可见的) |
| `send_button_sels` | 发送键;**为空或全禁用时退回 Enter** |
| `send_retry_sels` | 第一次点击没被吃掉(输入框没清空)时的兜底键 |
| `message_root_sels` | 助手回复根节点,取最后一个当"本回合的回复" |
| `markdown_body_sels` | 回复正文块;只读这些块,避开头像/工具栏等 chrome |
| `thinking_sels` | 思考过程节点,抓取前整块摘掉 |
| `stop_sels` | 生成中标记。停止键不一定带 `aria-label`(ChatGPT 是 `data-testid`、千问是 `data-is-streaming`、Gemini 是 `.stop-icon`) |
| `complete_sels` | 收尾标记。最后一个回复根里/之后找不到它 = 本回合仍在生成 |
| `fill` | `Standard`(textarea setter + `insertText`)或 `Paste`(合成粘贴,单次事务) |
| `clear_classes` | 填充前从输入框摘掉的类名(Gemini 的 `ql-blank`) |
| `beforeinput` | 填充前是否先派发 `beforeinput`(Quill 依赖) |
| `paste_if_send_disabled` | 填完发送键仍禁用时,select-all 后补一次合成粘贴 |

## 新增一个站点

四处都要改,**缺一处就会被清洗函数挡掉或探测不到**:

1. `src-tauri/src/webchat/sites.rs` —— 加一个 `SiteAdapter` 常量 + `adapter()` 里的分支,
   并把新 id 加进测试的 `ALL_SITES`(漏配分支会当场炸)。
2. `src/storage/configStore.ts` —— `WEBCHAT_SITE_IDS` 加 id(类型与两个清洗函数的白名单
   都由它派生)。
3. `src/engine/webchat.ts` —— `WEBCHAT_SITES` 加一条显示名。
4. `src/settings/settingsCatalog.tsx` —— 网页版生成那两条的 `keywords` 补上站点名,
   否则设置页搜索找不到。

## 排查

- **ask 稳定地跑满超时** → 先看该站点的 `complete_sels`:站点把这组按钮拿掉后,
  "本回合没结束"永远成立。这是 ChatGPT 侧"最近变慢"的第一嫌疑点。
- **报"提示词未能写入输入框"** → 输入框选择器过期,或填充策略不对(该走粘贴的站点
  用了 `insertText`)。填充判定只比可见字符(忽略换行与连续空白),富文本重排不会误判。
- **报"页面上找不到输入框"** → 多半是没登录(未登录站点通常不渲染输入框)。
- **回复抓回半截** → `message_root_sels` / `markdown_body_sels` 里混进了嵌套节点,
  或 `stop_sels` 没覆盖该站点的生成中标记。

## 页面活性恢复(软唤醒 → 激活脉冲 → 独立窗口)

后台标签页可能被浏览器/系统节流成"页面活着但模型不动"。恢复逻辑集中在
`src-tauri/src/webchat/activity.rs`(深模块)与 `webchat.rs` 的派发点,对调用方
(`askConversation`)完全透明:

- 梯子(WaitingForStart):发送后 6s 无进展软唤醒① → 15s 激活脉冲① → 30s
  软唤醒② → 45s 激活脉冲② → 60s 仍无进展 → 判定活性失败。流式期(生成中,
  busy 恒真)只看文本:20s 无变化软唤醒、之后每 45s 一次脉冲;不提前重发,
  受总超时约束。任何进展(count↑/文本指纹变化/长度↑/busy 否→是)计时清零。
- 软唤醒:挂常驻 `PageSession`(会话态 Emulation 覆盖必须连着才有效),
  `setWebLifecycleState(active)` + 焦点/空闲模拟 + `window.focus()`;
  不切标签页、不抢焦点、不 reload。
- 激活脉冲:一次性 `Page.bringToFront`,全局 1.5s、同目标 10s 节流
  (`PulseCoordinator`)。
- 站点健康(`SiteHealthBook`,按站点分账):本请求双脉冲耗尽仍停滞,或近 5 轮
  3 轮依赖脉冲 → `DedicatedPending`;当前消息以 typed 错误「页面长时间无进展」
  收场,前端两段式恢复换代 + 全量上下文重试,下一次会话重建点
  (`reset:true`)创建独立窗口(`Target.createTarget newWindow`,同 profile
  免登录)。进行中的会话绝不中途迁移。
- 只有活性失败才升级:登录失效/验证码/选择器失效/网络断开/发送后页面丢失/
  取消/解析失败都不算(换窗口解决不了,保留原错误分类)。
- 用户覆盖(设置页每站点下拉,存 `webchatSiteModes`,启动时前端回放 Hub):
  自动恢复(推荐)/始终使用标签页(仍软唤醒+脉冲,禁止升级)/始终独立窗口;
  升级后的站点提供「重新评估该站点」手动降级,无自动降级。
- 诊断:轨迹按 `requestId` 有界表(`webchat_take_trace` 拉取即删,双模型并行
  互不覆盖);阶段标记 `activity:soft_wake_N` / `activity:pulse_N` /
  `activity:soft_wake_recovered` / `activity:pulse_recovered` /
  `activity:promote_pending` / `activity:promote_rejected`,并附
  visibility/focus/idle 秒数(不含提示词与回复正文)。

## 线程身份(thread_urls)与两条路由的标签页互斥

**续聊的定位 = 会话键对应的站点线程 URL + 专属标签页,不再是"同 host 的那个标签页"。**

- 记录:每个成功回合结束后抓一次 `location.href`,存进 `HubState.thread_urls`
  (会话键 → 线程 URL,独立 5s 预算,失败静默,prompt 兜底仍在)。站点侧会话
  URL 带线程 id(chatgpt `/c/<id>`、deepseek `/a/chat/s/<id>`、豆包 `/chat/<id>`),
  这就是会话的站点侧身份。
- **表独立于会话槽,且落盘持久化**(`webchat-threads.json`,App 启动时载入,
  捕获/释放时原子写回):Edge 重启/端口漂移会 epoch+1 并清空 conversations,
  App 重启更会清空全部进程内存——但站点侧线程在服务端还活着。不持久化的话,
  重启后的第一条续聊会认领到入口残留页开新线程(豆包"续聊新建标签页"的
  顽固路径)。只有显式 release(换代/剧场收尾)才清除;闲置清扫关页但保留
  记忆,同键续聊仍可恢复。
- 恢复:下一轮 ask 发现句柄丢失,或**句柄仍活但页面 URL 已不是记住的线程**
  (认领到入口残留页,轨迹 `target_url_mismatch`)时——先找现存同 URL 页直接
  认领(不开重复页),没有才 `create_page` 直达同一会话(轨迹 `thread_restored`,
  `turn_count` 不清零);URL 失效才回落认领/新建。发送前页面殉职的中途重建
  (`recreate_target`)同样优先按线程种子,避免会话分叉。URL 比较剥尾斜杠后
  相等或前缀命中(站点追加 query 不误判)。
- 作废:`reset`(前端换代/15 轮上下文卫生)与换站点 = 显式开新会话,本轮不作
  恢复,新页落站点入口。Shared 路由(主演出单发)不记录线程——它的每条 prompt
  本来就带全量上下文,钉住线程反而是污染。
- 互斥:`claimed_targets` 现在**双向**挡串——Conversation 路由认领时不看 Shared
  在飞占用的页(原有),Shared 路由(`find_or_create_shared`)也跳过已认领页,
  选中/新建的页登记占用、ask 结束清账。主演出从此抢不走群聊/AI 剧场的会话页,
  反之亦然。

**前端配套语义(`ChatSession` / `webchatActor`):**

- 统一清空(`chatSession.reset()`)对 A/B/C 的网页适配器逐个 `invalidate()`:
  release 旧键标签页 + generation+1,下一轮 `reset:true` 全量重建——旧站点线程
  绝不污染清空后的会话(此前注释承诺了但实现没做)。
- 绑定热切换(`resolveReal` key 变)先 `dispose` 旧适配器再换新,旧键标签页当场
  回收,不等 30 分钟闲置清扫。前提是 `ensureConfig` 每次 send 重读配置(configStore
  在 `config-changed` 时整体替换缓存 Promise)——此前配置被长缓存,设置页改绑定
  后热切换永远拿不到新配置。
- 线程恢复的保障在 Rust 槽内;前端刷新/重启后适配器重建,首轮 fresh 不 reset,
  复用存活槽(含 `thread_url`),全量上下文随 prompt 兜底,语义不变。
