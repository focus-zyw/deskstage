# 角色对话系统设计方案

## 1. 目标

把现有的“LLM 生成一组台词并顺序播放”升级为一个有完整生命周期的对话系统，使甲乙长期表现为两个稳定、互相了解、会因事件改变关系的角色。

优先解决五个体验指标：

1. **角色可辨认**：遮住名字也能从措辞、判断方式和反应速度分辨是谁。
2. **接话有因果**：每句都在回应上一句，同时推进当前冲突，不是轮流发表段子。
3. **单集有弧线**：前提、升级、揭晓、回收能够被程序验证和完整保存。
4. **跨集有连续性**：老梗、未结事件、关系变化和用户选择能在之后自然生效。
5. **能被打断和接回去**：用户加入后，角色能回应并决定继续、转向或结束，而不是另开一条失忆的聊天链路。

## 2. 现状判断

项目已经具备很好的底座：

- `persona.ts` 是角色身份的唯一事实源。
- `promptBuilder.ts` 已包含场景卡、临时关系、长期关系、角色世界、环境和用户选择。
- `dialogSchema.ts` 已集中清洗台词与演出字段。
- `PerformancePlayer` 已支持 TTS 驱动节奏、动作、停顿和中途选择。
- `storyStore.ts` 已分离观众记忆与角色共同记忆，并支持老梗、事件线、连续剧情和 bond。
- `dialogPrefetch.ts` 已具备预生成能力。

当前瓶颈主要是这些能力没有被一个完整的 Episode 生命周期收拢：

- 场景卡虽然被解析，但没有进入 `PerformanceScript`、播放器、历史或蒸馏流程，无法验证“台词是否完成了场景卡”。
- prompt 要求“两人交替、分支完整、结尾回收”，解析层却只做字段清洗，结构不合格的剧本仍可能播放。
- 分支前半段和选中分支分别调用 `appendHistory`，会产生两个时间戳；对用户是一集，对存储却可能是两集。
- 完播蒸馏在选边后只看到当前分支，可能丢失分支前的铺垫。
- 用户聊天是无会话历史的单角色单句回复；另一角色只有视觉反应，不会真正接话。
- `generateDialog` 同时负责取上下文、随机决策、消费互动 recap、调用模型和解析。预生成也调用它，因此“准备内容”和“真正播出后提交状态”之间缺少清晰区分。
- 长期关系主要由拖拽距离改变，对话里的和解、背叛、兑现承诺和用户站队没有形成关系事件。

## 3. 核心设计：DialogueDirector 深模块

新增一个 `src/dialogue/` 目录，把对话生命周期放进一个深模块。外部调用方只学习三个动作：准备、响应事件、提交结果。

```ts
export interface DialogueDirector {
  prepare(request: DialogueRequest, signal?: AbortSignal): Promise<DialogueSession>
  react(sessionId: string, event: DialogueEvent, signal?: AbortSignal): Promise<DialoguePatch>
  commit(sessionId: string, result: SessionResult): Promise<void>
}
```

- `prepare`：冻结本轮上下文，生成并校验剧本；不得消费长期状态。
- `react`：处理用户插话、选择、戳角色等运行中事件，返回可追加或替换的短回合。
- `commit`：只在播出结果确定后，原子写入整集历史、关系事件和角色世界。

调用关系：

```text
播放/聊天/主动调度
        │
        ▼
  DialogueDirector
  ├─ ContextAssembler   冻结本轮上下文快照
  ├─ EpisodeWriter      调用 LLM 生成整集或短回合
  ├─ ScriptValidator    结构校验、质量评分、定点修复
  └─ OutcomeCommitter   一次性提交历史、记忆与关系变化
        │
        ▼
 PerformancePlayer + TTS + Stage
```

`ContextAssembler`、`ScriptValidator` 等先作为模块内部实现，不为每个文件暴露一套公共接口。LLM 是真实外部依赖，在 director 内接受一个 completion adapter；生产使用现有 `llmGateway`，测试使用内存 adapter。

## 4. 统一领域模型

### 4.1 DialogueRequest

```ts
interface DialogueRequest {
  source: 'manual' | 'prefetch' | 'proactive' | 'user-chat' | 'live'
  mode: Mode
  topic?: string
  topicPolicy: 'fixed' | 'suggested' | 'continue'
  interactive: boolean
}
```

`topicPolicy` 代替现在容易混淆的 `topicFixed` 与 `continueFromPrevious` 布尔组合。

### 4.2 ContextSnapshot

每次 `prepare` 时生成不可变快照：

```ts
interface ContextSnapshot {
  personas: Record<'A' | 'B', PersonaSnapshot>
  audience: AudienceContext
  relationship: RelationshipSnapshot
  story: StorySelection
  recentEpisodeSummaries: string[]
  pendingChoice?: UserChoiceMemory
  interactionRecap?: string
  environment?: string
  createdAt: number
}
```

规则：

- 预生成只保存快照和剧本，不更新 `lastInjectedAt`、不清空 recap、不推进 arc。
- 真正开始播放时标记素材为“已采用”；完整播出后才 `commit`。
- 新主题只带结构化摘要，不带上一集原始台词；只有 `continue` 才带最近 2～4 个 turn。

### 4.3 SceneBlueprint

保留并强化现有场景卡：

```ts
interface SceneBlueprint {
  premise: string
  relationship: string
  goalA: string
  goalB: string
  hiddenFact: string
  beats: Array<{
    id: string
    purpose: 'setup' | 'pressure' | 'reversal' | 'payoff'
    change: string
  }>
  callbackSeed: string
  ending: 'closed' | 'open-loop' | 'choice'
}
```

场景卡不再只是给模型看的草稿，而是剧本的正式组成部分。每句台词记录 `beatId`，校验器据此检查每个 beat 是否真的落地。

### 4.4 DialogueTurn

在现有 `DialogLine` 上只增加能产生实际价值的字段：

```ts
interface DialogueTurn extends DialogLine {
  id: string
  target: 'A' | 'B' | 'audience' | 'room'
  intent: 'ask' | 'answer' | 'challenge' | 'deflect' | 'reveal' | 'support' | 'payoff'
  beatId: string
  replyTo?: string
}
```

- `target` 解决“这句话到底对谁说”的问题，也让场外角色和观众插话时的听者动作不再靠猜。
- `intent` 用于校验接话是否推进，不直接展示给用户。
- `replyTo` 支持打断后接回、分支合流和调试。
- `action`、`delivery`、停顿继续沿用当前字段，播放器不需要理解戏剧逻辑。

### 4.5 DialogueSession / Episode

```ts
interface DialogueSession {
  id: string
  status: 'prepared' | 'playing' | 'awaiting-choice' | 'completed' | 'interrupted'
  request: DialogueRequest
  context: ContextSnapshot
  blueprint: SceneBlueprint
  before: DialogueTurn[]
  choice?: ChoicePoint
  branches: Record<string, DialogueTurn[]>
  selectedBranch?: string
}
```

历史按稳定 `episodeId` 一次提交完整对象，不再用 `Date.now()` 的一次 append 隐式定义“一集”。JSONL 可继续使用，但一行存一集对象，或所有台词共享调用方传入的固定 episodeId。

## 5. 两条生成路径

### 5.1 点播演出：整集预生成

保留现有体验优势，不在第一阶段改成逐句请求模型。

流程：

1. 选择话题、arc 与关系局势，生成 `ContextSnapshot`。
2. 一次生成 `SceneBlueprint + DialogueTurn[] + branches`。
3. 运行确定性校验。
4. 只有失败项才发起一次定点修复，例如“补齐 option B 的 3 句，不改其他台词”。
5. 统一补演出 cues；当前生成和预生成走同一规则。
6. 播放器只消费通过校验的 turn。
7. 完成或中止后，通过 `commit` 一次提交真实播出的完整路径。

这样既保留完整包袱和预取速度，也避免逐句 LLM 带来的停顿、成本和前后设定漂移。

### 5.2 用户聊天与插话：短回合增量生成

将现在的“指定角色回一句”改成 `TurnBatch`：

- `@甲`：甲必须先答；乙可在确有新信息或包袱时补 1 句。
- `@乙`：同理。
- 未指定：director 根据问题相关性、上一位说话者和连续发言次数选首答者。
- 默认生成 1～3 句，不强制两人都说，避免每次互动都像报幕。
- 维护最近 8～12 个 turn 的短期会话窗口，超出后压成摘要。
- 演出中插话先进入事件队列，在当前句结束的安全点处理；返回 `resume`、`branch` 或 `end` 决策。

```ts
type DialogueEvent =
  | { type: 'user-message'; text: string; target?: 'A' | 'B' }
  | { type: 'choice'; optionId: string }
  | { type: 'poke'; target: 'A' | 'B' }
  | { type: 'stop' }
```

第一版只需支持 idle 状态下的多轮聊天；演出中插话可作为后续迭代，避免同时改播放器状态机和生成链路。

## 6. 对话质量规则

### 6.1 确定性结构校验

`ScriptValidator` 在本地完成：

- 台词数量和单句长度在模式允许范围内。
- A/B 不连续霸占发言；允许为喜剧节奏出现最多 2 句连说，而不是绝对机械交替。
- 每个 `beatId` 至少有台词承载，顺序符合 blueprint。
- 每个 choice 恰好两个 option，且每个分支存在、长度合格、最终能收束或明确开放。
- `replyTo` 指向已存在的 turn。
- action、delivery、停顿合法。
- 同角色口头禅、强情绪和相似句不过量。
- 观众隐私事实不出现在 `challenge/payoff` 类型台词里。

### 6.2 轻量质量评分

本地可先实现的指标：

- 连续两句文本相似度。
- 角色特征词过度重复率。
- 问句是否在后续 1～2 turn 获得回应。
- `setup → pressure → reversal → payoff` 覆盖率。
- 最后两句是否引用前文实体或 callback seed。

不要让第二个 LLM 每次重写整集。低于阈值时，只发送 blueprint、失败规则和相关 turn 做局部修复；仍失败则使用当前可播放版本或内置剧本。

### 6.3 角色差异不靠口头禅堆砌

把人设拆为四个稳定维度，提示词和评测都围绕维度，而不是只要求“像甲/像乙”：

- **注意力偏好**：甲先看人和机会，乙先看规则和漏洞。
- **判断方式**：甲联想、夸张、先结论；乙求证、拆前提、后发制人。
- **风险姿态**：甲冒进找补，乙保守但会被激将。
- **情感防御**：甲用热闹掩饰心虚，乙用冷淡掩饰关心。

口头禅设冷却，例如每角色每集最多 1～2 次。这样即使不用“好家伙”“就这”，角色仍然可辨认。

## 7. 记忆与关系更新

将状态分成三层：

1. **会话短期状态**：当前前提、已公开事实、未回答问题、情绪和正在进行的 beat；随 session 结束释放。
2. **角色共同记忆**：老梗、未结事件、剧情 arc；只从真实播出的完整路径蒸馏。
3. **关系事件账本**：先记录具体事件，再聚合到 trust/rivalry，避免数值变化没有来由。

```ts
interface RelationshipEvent {
  episodeId: string
  kind: 'support' | 'betrayal' | 'repair' | 'rivalry' | 'user-sided'
  actor: 'A' | 'B' | 'audience'
  target: 'A' | 'B'
  weight: number
  summary: string
}
```

更新原则：

- 一集最多产生 1 个关系事件，单次变化要小。
- 中止的演出不推进 arc，不蒸馏 callback；若用户确实完成了选择，可单独记选择事件。
- 关系状态影响表达姿态，不覆盖角色基础人格。
- 预生成没有权力修改任何长期状态。

## 8. 推荐目录

```text
src/dialogue/
  director.ts          # 唯一对外 interface
  types.ts             # request/session/turn/result
  contextAssembler.ts  # 内部：冻结上下文
  episodeWriter.ts     # 内部：整集与短回合生成
  validator.ts         # 内部：确定性校验与评分
  repair.ts            # 内部：定点修复
  outcomeCommitter.ts  # 内部：一次性提交历史/剧情/关系
  prompts/
    blueprint.ts
    episode.ts
    turnBatch.ts
```

现有模块的去向：

- `promptBuilder.ts` 拆成 `prompts/*`，但仍由 director 隐藏，不让 `App.tsx` 组 prompt。
- `llmClient.ts` 保留通用 completion 与非对话工具调用；对话编排迁入 director。
- `dialogSchema.ts` 升级为 `DialogueTurn` 和 `DialogueSession` 的清洗入口。
- `dialogPrefetch.ts` 只调用 `director.prepare({ source: 'prefetch' })`。
- `historyStore.ts` 改为按 episodeId 原子保存完整播出路径。
- `PerformancePlayer` 继续只管可靠播放，不承担生成、记忆或剧情判断。
- `App.tsx` 只负责把 UI 事件翻译为 request/event，把 patch 交给播放器。

## 9. 分阶段落地

### P0：修正 Episode 生命周期

- `PerformanceScript` 保留 scene card。
- 引入稳定 episodeId 和 session status。
- 分支前后按同一个 episodeId 保存，蒸馏时传入完整已播路径。
- 补齐 choice 分支、turn 顺序和最后收束的校验。

验收：一次带选边的演出，在历史中只出现一集；回放、收藏和蒸馏看到的内容完全一致。

### P1：引入 DialogueDirector

- 收拢上下文冻结、随机决策、生成、校验和提交。
- 消除预生成阶段对 recap、arc、story 注入冷却的副作用。
- 当前生成与预生成统一经过 cues 与校验。

验收：给定固定 ContextSnapshot 和随机种子，生产 adapter 与测试 adapter 都通过同一组行为测试。

### P2：角色差异与接话质量

- 人设改为四维行为画像。
- 引入 target、intent、beatId、replyTo。
- 增加局部修复和离线评测集。

验收：盲测角色辨识率、问答承接率、beat 覆盖率和重复率达到设定阈值。

### P3：多轮聊天

- 用户聊天改为 1～3 句 TurnBatch。
- 加短期窗口与摘要。
- 甲乙能基于对方刚才的回答补充、反驳或收尾。

验收：连续追问 5 轮不丢主题；未点名时不机械轮换；被点名角色总是先答。

### P4：演出中插话

- 当前句结束点作为安全 seam。
- 用户事件触发 resume/branch/end。
- 记录真实播放路径，未播放分支永不进入记忆。

验收：插话不会重叠 TTS、不会丢气泡、不会把未播台词写入历史。

## 10. 测试与评测

行为测试应围绕 `DialogueDirector` 的 interface，而不是逐个测试内部 prompt 拼接函数：

- 固定上下文生成可播放 session。
- 缺失分支时执行定点修复或明确降级。
- 预生成不改变长期状态。
- 中止后只提交真实播放部分，且不推进剧情 arc。
- 完成选边后只提交所选路径，并保留分支前铺垫。
- 多轮聊天中 @角色优先级、连续发言限制、短期事实承接正确。

另建 20～30 个固定场景的离线评测集，至少记录：

| 指标 | 建议首版目标 |
| --- | ---: |
| JSON/结构一次通过率 | ≥ 95% |
| choice 双分支完整率 | 100% |
| 角色盲测辨识率 | ≥ 80% |
| 问句两回合内承接率 | ≥ 90% |
| 单集 beat 覆盖率 | ≥ 90% |
| 明显重复/复读率 | ≤ 5% |
| 用户聊天首句响应时间 | ≤ 2.5s（未含慢速网页模型） |

## 11. 本轮设计结论

首要工作不是继续增加 prompt 细则，而是先完成 P0 和 P1：让场景卡、实际播放路径、历史、蒸馏和关系更新属于同一个 DialogueSession。完成这一步后，再做角色差异和多轮互动，调 prompt 才会产生可测量、可持续的收益。
